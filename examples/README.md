# ORM Examples

Standalone примери, демонстриращи ключовите архитектурни тези на библиотеката. Всеки пример е самостоятелен `.cpp` файл, който се изгражда чрез `CMakeLists.txt` в този каталог. `compile_commands.json` се изнася автоматично за работа с `clangd`-базирани редактори.

## Build

```bash
cmake -G Ninja -B build
ninja -C build
```

След това изпълни който и да е пример:

```bash
./build/01_capability_gating     # compile-time gating демонстрация
./build/02_query_anatomy         # constexpr заявка под static_assert
./build/03_relationships         # embed vs reference връзки
./build/04_async_task            # Task<T> и nested co_await
```

## Списък на примерите

### `01_capability_gating.cpp` — Компилаторът като първи валидатор

Една и съща SELECT...JOIN заявка срещу две системи за съхранение. По подразбиране се компилира към `SQLiteDB` (минава). Разкоментирай `#define ORM_DEMO_DB_MONGODB` на ред 18, за да видиш как компилаторът отказва същата заявка срещу `MongoDB` с readable `static_assert` съобщение — документната семантика няма еквивалент на SQL JOIN върху външен ключ.

За реална демонстрация на провалящия се вариант чрез CMake:
```bash
cmake -B build -DORM_EXAMPLES_BUILD_FAILING=ON
ninja -C build 01_capability_gating_mongodb_fails   # ще пропадне
```

### `02_query_anatomy.cpp` — Анатомия на типизирана заявка

Изгражда заявка стъпка по стъпка (`select` → `where` → `order_by` → `limit`) и проверява структурата чрез `static_assert`. Илюстрира, че **цялата заявка е `constexpr` стойност**, а не низ. Програмата не извършва I/O — успешната компилация е доказателство, че заявката е валидна.

### `03_relationships.cpp` — `embed` срещу `reference`

Дефинира два варианта на `User`: единият със `store_as::reference` (нормализирано, postовете се пазят отделно), другият със `store_as::embed` (денормализирано, постовете се вграждат в родителя). Едно и също описание води до различна материализация в SQL (foreign key + JOIN), MongoDB (вложен документ), Redis (key prefix) и Neo4j (ребра).

### `04_async_task.cpp` — Корутинна задача

Минимален пример за `orm::Task<T>` --- мързеливо стартиране, връщане на стойност, nested композиция, и безопасно прехвърляне на изключения. Илюстрира `sync_wait()` като мост към некорутинен код.

## IDE setup

Файлът `.clangd` в този каталог дава на LSP сървъра базови `-I` пътища, така че да резолва ORM заглавните файлове **дори преди първи `cmake` run**. След като изпълниш `cmake -G Ninja -B build`, генерираният `compile_commands.json` се копира до текущия каталог и `clangd` го предпочита за пълно автодопълване и грешки в реално време.

Проверено с:
- **VS Code** + `vscode-clangd` extension
- **NeoVim** + `nvim-lspconfig` + `clangd` сървър
- **CLion** (използва `compile_commands.json` директно)

## Защо тези примери

Всеки пример таргетира конкретно архитектурно твърдение от дипломната работа:

| Пример | Твърдение |
|---|---|
| 01 | Компилаторът отказва структурно невалидни заявки --- грешка при компилация, не при изпълнение |
| 02 | Заявката е стойност от типовата система, не низ --- цялата ѝ структура е проверима по време на компилация |
| 03 | Един C++ модел се материализира по различен начин в различните системи за съхранение --- логиката е една, физиката е специфична |
| 04 | Асинхронното изпълнение е първокласна абстракция чрез `Task<T>`, не ad-hoc обвивка |

## Зависимости

- C++23 компилатор (тестван с GCC 14 на Linux/WSL и clang 21 на Windows)
- CMake ≥ 3.20, Ninja
- `libsqlite3-dev` (само за пример 01)
- Boost.PFR (auto-fetched от `CMakeLists.txt`, ако не е наличен в родителския build)
