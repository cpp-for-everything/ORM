# Демо за защитата — рунбук

Този каталог съдържа двете живи демонстрации, които вървят след слайдовете. Общ бюджет: **5 мин**.

## Out-of-the-box (от свеж клон, без локални инсталации)

На macOS / Linux / Windows с Docker Desktop:

```bash
git clone <repo>
cd <repo>/doc/v2/bg_presentation/demo
docker compose up
```

Това вдига MariaDB сайдкара, изгражда демо контейнера (еднократно, ~3 мин при първи build), и автоматично пуска двете демонстрации. Подходящо за:
- Свеж клон на нова машина (например лаптопа за защитата)
- Демо без инсталирани GCC / CMake / Boost.PFR / SQLite / liburing / libmariadb на host-а
- Гарантирано идентично поведение независимо от ОС

За интерактивна работа (по време на защита):

```bash
docker compose run --rm demo bash
# вече вътре в контейнера:
bash doc/v2/bg_presentation/demo/run_demo_a.sh
bash doc/v2/bg_presentation/demo/run_demo_b.sh
```

`docker compose down` спира MariaDB и почиства мрежата.

## Структура

| Файл | Цел |
|---|---|
| `run_demo_a.sh` | На сцената: компилира MongoDB (fail) → SQLite (pass) през bash |
| `run_demo_b.sh` | На сцената: `bench_async` + бонус MariaDB |
| `prewarm.sh` | Един път преди защитата — сглобява всичко, кешира |
| `README.md` | Този рунбук |

**Source файлът за Demo A живее в `examples/01_capability_gating.cpp`** на корена на хранилището — там стои наред с другите standalone примери, със собствен `CMakeLists.txt` и `.clangd`. Този каталог съдържа само scripts за оркестрация на сцената.

## IDE setup (един път, у дома)

```bash
wsl -d Ubuntu-24.04 -- bash -c '
    cd /mnt/d/GitHub/ORM/examples &&
    cmake -G Ninja -B build &&
    ninja -C build
'
```

След това при отваряне на `examples/01_capability_gating.cpp` в редактор:
- clangd чете `compile_commands.json` (копиран в source dir от CMakeLists)
- Резолва всички ORM заглавни файлове, дава пълно автодопълване
- Ако разкоментираш `#define ORM_DEMO_DB_MONGODB` на ред 18 — static_assert грешката се появява **на ред със squiggle върху `facade << q`** без пресглобяване

## Преди защитата (един път)

```bash
wsl -d Ubuntu-24.04 -- bash /mnt/d/GitHub/ORM/doc/v2/bg_presentation/demo/prewarm.sh
```

Изпълнението отнема ~30 s (~50 s ако Docker е стартиран). След това:
- `bench_async`, `test_async_unit`, `test_mysql_async_coroutine_probe` са сглобени
- Демо A е компилирано и кеширано
- Демо B е загряло OS caches
- MariaDB Docker контейнер е стартиран (ако Docker работи); ако не — Демо B пропуска бонуса автоматично

## На сцената

Отворете **един** WSL терминал. Изпълнявайте едно по едно.

### Демо A — Компилаторът е първи валидатор (~1 мин 30 с)

```bash
bash /mnt/d/GitHub/ORM/doc/v2/bg_presentation/demo/run_demo_a.sh
```

**Какво се случва:**
1. Компилираме `demo_a_capability.cpp` с `-DORM_DEMO_DB_MONGODB`. Компилаторът отказва с четим `static_assert`:
   > orm::db: this connector does not support JOIN operations. Remove .join() clauses, use store_as::reference relationships, or switch to a connector that declares `using supports_joins = void;`.
2. Превключваме на `-DORM_DEMO_DB_SQLITE`. Компилацията преминава, програмата работи.

**Какво да кажете:**
> Тук имаме една и съща C++ заявка с `.join(...)`. Когато я насочим към MongoDB, компилаторът отказва — конекторът за MongoDB не декларира `supports_joins`, защото документната семантика няма еквивалент на SQL JOIN върху външен ключ. Сменям един ред — `using DemoDB = orm::SQLiteDB;` — и същата заявка компилира успешно, защото SQLite декларира тази способност. Това е централната теза на работата: грешката не е в тестовете, а в компилатора, който отказва да я приеме.

**Ако нещо се счупи:** покажете слайда с `static_assert` примера и кажете „пълният live cycle е във видеото в линка". Имайте записан скрийнкаст като резерва.

### Демо B — Корутинен async vs синхронен (~2 мин 30 с)

```bash
bash /mnt/d/GitHub/ORM/doc/v2/bg_presentation/demo/run_demo_b.sh
```

**Какво се случва:**
1. Изпълнява `bench_async` с три случая (4 нишки × {100,1000} задачи × {100,1000} µs изчакване).
2. Извежда таблица с очаквания тренд: ~1× / ~5× / ~12×.
3. Ако MariaDB е достъпна — пуска и емпиричната проба на `_start`/`_cont` срещу жива база (4 теста, ~300 ms).

**Какво да кажете:**
> Същият експеримент, който е документиран в Таблица 6 на Глава 4. Числата варират според хардуера, но тенденцията е винаги една и съща: при доминираща фаза на изчакване, корутинният модел освобождава работните нишки и пропускливостта расте многократно. Бонусът, ако MariaDB е достъпна, показва същото върху жива база през неблокиращите `mysql_*_start`/`_cont` функции.

**Ако MariaDB не отговори:** Демо B автоматично пропуска бонуса с жълто съобщение. Бенчмаркът винаги работи.

## Допълнителна вариация: live IDE „wow" момент

Ако имаш проектор който показва редактора (vscode + clangd), можеш да направиш:

1. Преди да започнеш Демо A през shell-а — отвори `demo_a_capability.cpp` в редактор
2. Покажи че всичко е зелено (clangd resolved-ва)
3. Разкоментирай ред 18: `#define ORM_DEMO_DB_MONGODB`
4. **Без билд**: clangd мигновено показва червена линия върху `facade << q` (ред ~76)
5. Hover-ни линията — tooltip-ът показва същия static_assert message от компилатора
6. Коментирай го обратно — squiggle изчезва
7. След това пусни `run_demo_a.sh` за reproducibility през compiler

Този двоен ход (IDE → терминал) е особено мощен за демонстрация на тезата „компилаторът е първи валидатор".
